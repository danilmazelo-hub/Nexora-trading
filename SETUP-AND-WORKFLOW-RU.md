# Как запускать проект и идти по плану

Эта инструкция для человека, который работает с ИИ-агентом. Сначала создаётся приложение по D00–D02. В этой папке лежат только документы, поэтому запускать `pnpm dev` прямо в ней сейчас нельзя.

## 1. Подготовь рабочее место

- Установи Git, редактор с ИИ-агентом, Node.js и Docker Desktop для Windows. В D01 агент сверяет официальные инструкции/совместимость и фиксирует точные версии Node и pnpm. Базовый ориентир — Node 24.x, pnpm 10.x; произвольное обновление до latest во время задачи не требуется.
- Запусти Docker Desktop и дождись готовности. Если требуется WSL2/виртуализация или перезагрузка, заверши настройку по официальной инструкции Docker до проверки БД.
- Создай отдельную локальную папку `C:\dev\easytrade`. Документы и снимки не должны оказаться в public-каталоге сайта или production-артефакте. Исходный код удобно держать вне синхронизируемой папки OneDrive, чтобы процессы сборки и зависимости не конфликтовали с синхронизацией.
- Открой папку приложения как проект редактора. Не открывай случайно текущий ComfyUI-проект и не создавай EasyTrade внутри него.

В PowerShell проверь наличие инструментов:

```powershell
node --version
npm --version
git --version
docker --version
docker compose version
```

Сохрани версии в отчёте D01. Если команда не найдена, реши установку до изменения прикладного кода. Полный лог с ключами и содержимым .env в чат не вставляй.

## 2. Первый запрос агенту — D00

Передай пакет документов и скопируй шаблон из [TASK-PROMPT-TEMPLATE-RU.md](TASK-PROMPT-TEMPLATE-RU.md), указав ID D00 и `C:\dev\easytrade`. Агент создаёт систему правил/архитектуру/инвентаризацию экранов. Пока он не должен разрабатывать сразу все функции.

Твоя проверка: в проекте есть корневые и профильные правила, ссылки открываются, план задач сохранён, два этапа разделены. Прочти краткий отчёт и отметь D00 в своей карте. Затем отправь новый запрос на D01.

## 3. Команды — договор для создаваемого проекта

Это **требуемые имена команд**, которые агент должен реализовать и проверить в D01–D06. Они не существуют автоматически от наличия этого документа. Если агент выбрал другой технически обоснованный способ, он синхронно обновляет package scripts, README и копию этой инструкции в проекте, а затем показывает работающий запуск.

| Команда из корня приложения | Что обязана делать | Готовность |
|---|---|---|
| `pnpm dev` | Запустить web и API с понятными адресами/логами | D01 |
| `pnpm dev:web` / `pnpm dev:api` | Запустить только одну часть для диагностики | D01 |
| `pnpm lint` | Проверить стиль без автоматической перезаписи файлов | D01 |
| `pnpm typecheck` | Проверить типы web/API/contracts | D01 |
| `pnpm test` | Однократно выполнить подходящие unit-тесты, без watch | D01 и далее |
| `pnpm test:integration` | Выполнить интеграционные тесты на отдельной тестовой БД | D05 |
| `pnpm test:e2e` | Запустить воспроизводимые сквозные сценарии | первые в D07, расширять по задачам |
| `pnpm build` | Собрать web и API и нужные пакеты, а не только default app | D01 |
| `pnpm db:generate` | Сгенерировать ORM-клиент | D02–D03 |
| `pnpm db:migrate` | Применить уже сохранённые миграции к локальной БД | D03 |
| `pnpm db:migrate:dev` | Создать новую именованную миграцию в dev-среде | D03, запускает агент при изменении схемы |
| `pnpm db:seed` | Идемпотентно заполнить справочник и демосценарии без удаления данных | D06 |

Для тестов агент документирует способ подготовки/очистки **тестовой** БД. Запуск тестов не должен очищать dev или production. Общий `pnpm build` не имеет скрытого deployment, миграции или seed.

## 4. Первый запуск после D06

Попроси агента показать реально созданные файлы и команды, а затем запусти сам. Ниже ожидаемый вариант для Windows; имена `.env.example` и Compose service `db` должны быть созданы по D01–D02.

```powershell
Set-Location C:\dev\easytrade
pnpm --version
pnpm install --frozen-lockfile
```

На самом первом создании lockfile агент делает установку и фиксирует его. Если менеджер сообщает о несовпадении lockfile, не удаляй его наугад: попроси агента объяснить расхождение.

Создай конфиг из `apps/api/.env.example` в `apps/api/.env` и `apps/web/.env.example` в `apps/web/.env`. Копируй только если целевого файла ещё нет; существующий конфиг не перезаписывай. Агент обязан указать имена локальной БД, порт и необходимые безопасные значения. Для demo внешние API-ключи не нужны. Тестовые значения пароля локального PostgreSQL — не пароль реального пользователя.

```powershell
docker compose up -d db
docker compose ps
pnpm db:generate
pnpm db:migrate
pnpm db:seed
pnpm dev
```

Ожидаемые адреса, которые фиксируются в README:

- web: `http://localhost:5173/demo`;
- API liveness: `http://localhost:3001/health/live`;
- API readiness с БД: `http://localhost:3001/health/ready`.

Frontend обращается к `/api` через dev proxy. Сессия передаётся серверной cookie; ключи и DATABASE_URL не попадают в браузерный bundle. Если порты изменились, агент обновляет конфиг и инструкцию вместе.

После запуска нажми «Войти в демо»: после D06 будет собственный счёт $50 000. После D07 пройди навигацию. До соответствующей задачи торговые/денежные функции ещё не готовы — не отмечай их по одному наличию кнопки.

## 5. Каждый следующий рабочий день

1. Открой карту и найди первый непринятый ID. Посмотри последний принятый commit.
2. Прочитай карточку в плане и отправь её по шаблону. Укажи текущее состояние и незакрытые ошибки.
3. Разреши агенту выполнить задачу, применимые проверки и исправления в её пределах. Он не должен молча перескакивать на следующий пакет.
4. При изменении схемы БД примени сохранённую миграцию и seed по инструкции задачи. Если непонятно, какую БД затронет команда, сначала уточни это у агента.
5. Запусти приложение, выполни «Моя проверка» из карты. Сравни ожидаемое и фактическое.
6. Прочитай результаты тестов: какая команда, сколько прошло/упало, что не запускалось и почему. Сообщение «тесты должны пройти» не является результатом.
7. Просмотри список изменённых файлов и итоговый diff. Проверь отсутствие секретов и случайных изменений чужих задач.
8. По правилам проекта сохрани проверенную задачу отдельным commit; публикация и merge выполняются по принятому процессу, а не автоматически. Запиши ID, commit и доказательство в карту.

Не обязательно запускать весь набор E2E после изменения одного текста. Агент выбирает проверки по риску; изменение ledger/order/auth требует соответствующих значимых тестов. Полный повторный прогон нужен на контрольных точках и перед релизом.

## 6. Что делать, если не работает

| Симптом | Первое действие |
|---|---|
| `pnpm` не найден | Сверить установку менеджера с точной версией из packageManager; заново открыть терминал |
| Docker не отвечает | Запустить Docker Desktop и проверить `docker compose ps`, не переустанавливать приложение |
| Backend не видит БД | Проверить контейнер db, DATABASE_URL/порт и применённые миграции; пароль в отчёте замаскировать |
| `/health/live` работает, `/health/ready` нет | Backend запущен, но зависимость не готова; изучить безопасное сообщение и лог |
| Порт занят | Определить собственный процесс или согласованно сменить порт; не завершать все node-процессы на компьютере |
| UI открылся, данные не пришли | Посмотреть readiness и вкладку Network: status/code/requestId; не редактировать баланс в браузере |
| Миграция упала | Сохранить текст ошибки и состояние миграций; не нажимать reset как универсальное исправление |
| Тесты падают | Вернуть тот же ID агенту с ошибкой; не удалять тест, чтобы получить зелёный результат |
| Агент пишет «готово», а кнопка не работает | Записать шаги/ожидание/факт, вернуть задачу «нужна правка» |

## 7. Как сообщить об ошибке агенту

```text
Задача: D17, commit <мой commit>.
Среда: Windows, браузер, размер окна, локальное demo.
Шаги: открываю BTC → Edit TP/SL → TP=1 → Save.
Ожидание: отказ и открытая позиция.
Факт: <что увидел>.
Доказательство: скриншот, code/requestId, безопасный фрагмент лога.
Исправь причину в рамках D17, сохрани остальные требования и повтори регрессию.
```

## 8. Остановка и сохранение данных

В терминале приложения нажми Ctrl+C. Локальную БД можно остановить командой `docker compose stop db`: volume остаётся. Для продолжения — `docker compose start db`, затем `pnpm dev`.

Не выполняй `docker compose down -v`, `prisma migrate reset` и команды `reset/clean` наугад: они могут удалить данные. Для демонстрации используй контролируемый reset только собственной демосессии из интерфейса.

## 9. Новая сессия агента и потеря контекста

Передай START-HERE, текущую карту, активный план, гайд правил и текущий ID/commit. Попроси сначала прочитать действующие правила приложения и проверить незакоммиченные изменения. Кратко укажи: что принято, что в работе, какая ошибка мешает. Не начинай весь проект заново и не передавай полный экспорт личной переписки.

## 10. Перед показом и перед live

Для демо выполни G7: чистый запуск, все обязательные экраны, A01–A17 и 10-минутный сценарий из приёмки. Для этапа 2 пройди R01–R14 в тестовых средах и независимую приёмку; только затем владелец принимает решение о R15. Live API-ключи не выдаются агенту просто для проверки демоформы.
