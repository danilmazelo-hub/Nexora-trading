# Как выдавать ИИ-агенту одну задачу

Человек выбирает ID в своей карте, агент читает техническую карточку. На каждую новую задачу заполни шаблон. Один ID означает полный небольшой сценарий: данные → сервер → UI → проверки; агент может разбить его на внутренние шаги, не расширяя объём.

## Основной шаблон

```text
Разрабатываем EasyTrade.
Папка приложения: <путь к отдельному репозиторию приложения>.
Папка переданного пакета документов: <локальный путь к этому пакету>.

Текущая задача: <D00, D01 ... или R01 ...>.
Последняя принятая задача/commit: <ID / hash либо «нет, новый проект»>.
Текущие незакрытые ошибки: <список либо «нет»>.

Прочитай:
1. START-HERE-RU.md.
2. Действующие корневые и применимые вложенные правила приложения.
3. AI-AGENT-PROJECT-STRUCTURE-GUIDE-RU.md и ARCHITECTURE-AND-DATA-RU.md.
4. Только нужную карточку и её зависимости из EASYTRADE-IMPLEMENTATION-PLAN-RU.md.
5. Связанные проверки ACCEPTANCE-AND-AUDIT-REGRESSIONS-RU.md.
6. Нужные разделы аудита/доказательств по ссылкам, если задача касается референса.

Сначала проверь состояние репозитория и пользовательские изменения.
Выполни выбранную задачу по порядку: данные/миграции → backend → frontend → проверка.
Не перескакивай к следующему ID. Не переписывай принятые функции без причины.
В D00 создай систему правил и карту документации по гайду; не реализуй все функции.
В D01 создай и проверь команды из инструкции запуска; фиксируй версии/lockfile.

Если задача требует нового пакета/SDK, проверь актуальную официальную документацию,
совместимость и лицензию. Не выдавай старые примеры за действующий API.

Сохраняй режим demo и предусмотренную изоляцию сессий.
Не подключай реальные платежи/адреса/документы/торговлю на этапе 1.
Не объявляй сценарную симуляцию реальным AI, MFA или KYC.

Доведи задачу до проверяемого результата в разрешённом объёме.
Если найден дефект зависимости, исправь его или явно зафиксируй блокер.
Не удаляй проверку, чтобы скрыть ошибку. Не меняй ожидаемое финансовое число под код.

В конце дай:
- ID и выполненный пользовательский сценарий;
- какие правила применены;
- изменённые файлы/миграции/контракты;
- фактически запущенные команды и результаты;
- что не проверено и почему;
- точные действия, которыми я проверю результат сам;
- необходимые команды запуска/применения миграций;
- существующий commit либо предложение проверенного diff для сохранения по нашему процессу.

Обнови docs/progress.md и docs/QA-results.md приложения.
В моей личной DEVELOPER-ROADMAP-RU.md не ставь отметку «принято» за меня.
```

## Если задача упала

```text
Продолжаем тот же ID <ID>. Результат пока не принят.
Действие: <что нажал/какую команду выполнил>.
Ожидание: <критерий плана>.
Факт: <ошибка или неправильное значение>.
Доказательство: <скриншот/code/requestId/безопасный лог>.
Найди причину, исправь минимально необходимое и повтори исходную проверку.
Сохрани остальные требования и пользовательские изменения.
```

## Когда можно давать следующий ID

Когда ты сам прошёл контрольное действие, применимые проверки завершены, нет блокирующих ошибок и результат сохранён. Само сообщение агента «готово» не является приёмкой. Сложную задачу можно делить на подзадачи внутри её карточки, но флажок ID ставится после всех её обязательных частей.
